# Batch Validation

> 정책이 불명확한 Batch를 코드 실행 여부가 아니라 **실제 데이터와 결과의 일치 여부**로 검증했습니다.

## 한눈에 보기

### 문제
외부 개발사가 작성한 기존 Batch와 AI를 활용해 재구성된 Airflow / Spring Batch Job이 있었지만, 주문·회원·통계의 **도메인 정책과 집계 기준이 충분히 정리되어 있지 않았습니다.**

### 판단
코드가 정상 실행되는지만 확인해서는 올바른 Batch인지 판단할 수 없었습니다. **원천 데이터 → 구현 조건 → 결과 데이터**를 함께 비교하고, 코드와 데이터만으로 결정할 수 없는 부분은 담당자에게 정책을 확인해야 한다고 판단했습니다.

### 한 일
- 기존 코드·원천 데이터·결과 데이터를 비교해 집계 조건 검증
- 상태값 및 포함/제외 조건 오류 수정
- 실제 데이터에서 발견한 예외 케이스를 Fixture와 테스트 케이스로 재현
- 재실행·실패 후 재처리·Backfill 시 멱등성 검증
- EC2 Airflow → ECS Fargate → Spring Batch 실행 구조에서 Job 결과 확인
- Docker + PostgreSQL + LocalStack 기반 로컬 반복 검증 환경 구성

### 결과
Batch를 단순히 **“실행되는 코드”**가 아니라, **정책 → 원천 데이터 → 집계 결과가 서로 일치하고 재실행해도 안전한 Job인지 검증하는 방식**으로 정리하고 있습니다.

---

## 왜 코드만 보고 판단할 수 없었나

신규 커머스 플랫폼에는 주문, 회원, 상품, 통계 등 여러 도메인의 Batch Job이 존재합니다. 기존 외부 개발사가 작성한 Job과 이후 AI를 이용해 Airflow / Spring Batch 구조로 재구성한 Job을 검증해야 했습니다.

가장 큰 문제는 코드 품질 자체보다 **정책의 빈칸**이었습니다.

| 확인 대상 | 검증 질문 |
| --- | --- |
| 주문 상태 | 취소 주문은 구매에 포함하는가? |
| 부분 취소 | 일부 상품만 취소된 주문은 어떻게 계산하는가? |
| 배송비 | 구매 금액에 포함하는가? |
| 쿠폰 | 할인 전/후 어떤 금액을 기준으로 하는가? |
| 환불 | 어느 시점의 환불까지 차감하는가? |
| 회원 | 탈퇴 회원은 집계하는가? |
| 미구매 회원 | Summary Row를 생성해야 하는가? |
| 재실행 | 같은 기준일로 다시 실행해도 결과가 동일한가? |

코드가 `COMPLETED`가 되는 것과 **비즈니스적으로 올바른 결과를 만드는 것**은 다른 문제였습니다.

## 검증 흐름

```text
기존 Batch 코드 ─┐
                  ├→ 구현 조건 비교 → 정책 명확? ─ No → 담당자 확인 ─┐
원천 테이블 → 실제 데이터 ┘                                      │
                                                                  ↓
                                                         예상 결과 정의
                                                                  ↓
                                                              Job 실행
                                                                  ↓
                                                           결과 테이블 비교
                                                             ↙          ↘
                                                        불일치          일치
                                                          ↓              ↓
                                                       로직 수정    재실행 / Backfill
                                                          └──────→      ↓
                                                                  멱등성 확인
```

1. 기존 구현이 어떤 조건으로 데이터를 읽는지 확인
2. 실제 원천 데이터에 어떤 상태와 예외가 존재하는지 확인
3. 결과 테이블에 어떤 값이 생성되는지 비교
4. 정책이 불명확하면 담당자에게 기준 확인
5. 예상 결과를 먼저 정의
6. Job 수정 및 재실행
7. 같은 Job을 다시 실행해도 동일한 결과가 나오는지 확인

## 사례 1. 구매하지 않은 회원은 존재하지 않는 회원인가?

회원 구매 통계 Batch에서는 처음 구현된 방식이 **구매가 존재하는 회원을 기준으로 집계를 시작**하고 있었습니다.

```text
order
  ↓
purchase aggregation
  ↓
member_purchase_summary
```

이 방식에서는 구매 기록이 없는 정상 회원이 결과에서 완전히 사라집니다.

| member_id | 상태 | 주문 |
| ---: | --- | --- |
| 101 | 정상 | 3건 |
| 102 | 정상 | 없음 |
| 103 | 정상 | 1건 |

기존 결과:

| member_id | purchase_count | purchase_amount |
| ---: | ---: | ---: |
| 101 | 3 | 120,000 |
| 103 | 1 | 35,000 |

`member_id=102`는 존재하지 않습니다. 하지만 서비스에서 다음 두 상태는 의미가 다를 수 있습니다.

```text
Summary 없음
```

```text
Summary 있음
purchase_count = 0
purchase_amount = 0
```

정상 회원 전체를 기준으로 LEFT JOIN하도록 변경하면 다음처럼 표현할 수 있습니다.

| member_id | purchase_count | purchase_amount |
| ---: | ---: | ---: |
| 101 | 3 | 120,000 |
| 102 | 0 | 0 |
| 103 | 1 | 35,000 |

핵심은 SQL의 `LEFT JOIN` 자체가 아니라 **“구매한 적이 없다”라는 상태를 시스템에서 어떻게 표현할 것인가**였습니다.

## 사례 2. 실제 주문 데이터로 집계 조건 검증

정상 주문 한두 건으로만 테스트하면 정책 오류를 찾기 어렵습니다. 주문 상태와 환불·삭제 여부 등을 조합해 케이스를 나눴습니다.

| Case | 주문/상품 상태 | 기대 결과 |
| --- | --- | --- |
| C1 | 정상 주문 | 구매 포함 |
| C2 | 결제 완료 | 구매 포함 |
| C3 | 전체 취소 | 구매 제외 |
| C4 | 부분 취소 | 유효 수량만 반영 |
| C5 | 배송 완료 | 구매 포함 |
| C6 | INPUT 상품만 존재 | 구매 제외 |
| C7 | 일부 Refund | 환불분 차감 |
| C8 | 삭제된 주문/상품 | 제외 |
| C9 | 게스트 주문 | 회원 통계 제외 |
| C10 | 구매 이력 없음 | 0 / 0 |
| C11 | 구매는 있으나 Summary 없음 | 신규 생성 |

Job 실행 전에 예상값을 만들고 실행 후 DB 결과와 비교했습니다.

```text
Fixture Data → Spring Batch → Result Table ─┐
Expected Result ────────────────────────────┤→ Compare
                                            ├─ mismatch → 원인 분석 / 수정
                                            └─ match    → 재실행 검증
```

## 재실행해도 안전한가

Batch에서는 첫 실행 성공보다 **두 번째 실행이 어떻게 되는지**를 중요하게 봤습니다.

- 동일 기준일로 재실행
- 중간 실패 후 재실행
- Backfill
- 기존 Summary Row가 이미 존재
- 원천 데이터에서 이전 집계 대상이 사라짐
- 과거 실행 결과가 남아 있는 상태

검증 기준은 단순했습니다.

```text
첫 실행 결과
     =
두 번째 실행 결과
     =
동일한 원천 데이터에서 기대하는 결과
```

특히 원천 데이터에서 더 이상 집계 대상이 아닌 데이터가 **과거 Summary에 계속 남아 있는 문제**까지 확인했습니다.

## 운영 실행 구조

AWS Managed Airflow 비용을 고려해 **EC2에 Apache Airflow를 직접 구성**했고, Spring Batch Job 전체는 **ECS Fargate Task**로 실행합니다.

```text
Apache Airflow (EC2)
        ↓
   Shell Script
        ↓
   ECS RunTask
        ↓
  ECS Fargate
        ↓
  Spring Batch
        ↓
   PostgreSQL
        ↓
 Task 종료 상태 / Exit Code
        ↓
 Airflow 성공·실패 판단
```

Job을 실행 요청하고 끝내는 것이 아니라 Task 종료 상태와 결과를 확인해 성공/실패를 판단합니다.

## 로컬 검증 환경

운영 AWS 환경에 의존하지 않고 수정과 검증을 반복하기 위해 로컬 환경을 별도로 구성했습니다.

```text
Docker Compose
 ├─ PostgreSQL
 ├─ LocalStack
 ├─ Airflow / Scheduler
 └─ Spring Batch
```

목표는 운영 환경을 완벽히 복제하는 것이 아니라 **데이터 생성 → Job 실행 → DB 확인 → 초기화**를 빠르게 반복하는 것이었습니다.

---

## 이 경험에서 중요하게 본 것

Batch 검증에서 가장 어려웠던 것은 Spring Batch API나 Airflow 사용법이 아니었습니다.

> **“이 숫자는 어떤 데이터를 의미해야 하는가?”**

정책이 부족한 시스템에서는 코드 역시 하나의 자료일 뿐 정답이라고 가정하지 않았습니다. 그래서 **코드, 실제 데이터, 실행 결과, 담당자의 정책**을 함께 확인하며 Batch를 검증하고 있습니다.
