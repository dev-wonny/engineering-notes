# Event Platform

> 이벤트 유형별 차이를 살리는 모델을 제안했지만, 조직의 데이터 모델 제약을 수용해 **최종 요구 안에서 구현 가능한 구조로 조정**했습니다.

## 한눈에 보기

### 문제
출석·랜덤 리워드·응모권은 참여 방식과 상태 전이, 보상 규칙이 다른데 하나의 범용 이벤트 테이블로 관리해야 했습니다.

### 판단
장기 유지보수 관점에서는 이벤트별 도메인 책임을 분리하는 편이 더 적합하다고 판단해 DDD 관점의 모델을 제안했습니다. 다만 최종 의사결정은 기존 회사에서 사용하던 범용 테이블 구조 유지였습니다.

### 한 일
- 이벤트 유형별 공통 속성과 개별 정책을 분리한 도메인 모델 제안
- 범용 테이블의 Nullable 증가와 확장 시 trade-off 설명
- DB 구조와 애플리케이션 도메인을 분리하는 안도 제안
- 최종 DB 중심 구조 요구를 수용해 기존 구현을 재구성
- Redis 기반 동시성 제어와 JWT 인증 흐름은 설계·제안까지 진행
- ECS(EC2) 환경 배포·운영, ELK 기반 로그 확인

### 결과
제가 제안한 구조가 최종 반영되지는 않았지만, **기술적으로 선호하는 안을 설명하고 의사결정자의 요구를 충분히 확인한 뒤 제약 안에서 시스템을 완성하는 경험**을 했습니다.

---

## 이벤트는 같은 이름의 하나의 도메인인가?

세 이벤트는 공통적으로 기간, 노출 상태, 제목 같은 메타데이터를 가질 수 있지만 핵심 정책은 다릅니다.

| 유형 | 핵심 정책 |
| --- | --- |
| 출석 | 날짜별 참여 여부, 연속/누적 출석 |
| 랜덤 리워드 | 추첨/확률, 보상 지급 |
| 응모권 | 적립, 사용, 당첨 처리 |

초기에는 다음과 같이 공통 메타데이터와 이벤트별 핵심 책임을 분리하는 방향을 생각했습니다.

```text
Event
 ├─ Attendance Event
 ├─ Random Reward Event
 └─ Entry Event
```

## 최종 요구: 하나의 범용 테이블

조직에서는 여러 이벤트 유형을 하나의 테이블과 설정값으로 표현하는 방식을 원했습니다.

```text
event
 ├─ id
 ├─ event_type
 ├─ common fields
 ├─ attendance fields    → 다른 유형에서는 NULL
 ├─ random reward fields → 다른 유형에서는 NULL
 └─ entry fields         → 다른 유형에서는 NULL
```

이 방식은 테이블과 조회 구조를 단순하게 만들 수 있지만, 이벤트 종류가 늘어날수록 사용하지 않는 컬럼과 조건 분기가 증가할 수 있다고 봤습니다.

| 관점 | 도메인 분리 | 범용 테이블 |
| --- | --- | --- |
| 유형별 정책 표현 | 명확함 | 조건 분기 필요 |
| Nullable 컬럼 | 적음 | 증가 가능 |
| 신규 이벤트 확장 | 별도 모델 추가 | 기존 테이블 확장 |
| 현재 조직 익숙함 | 낮음 | 높음 |
| 초기 구현 일관성 | 추가 설계 필요 | 기존 패턴 재사용 |

## 애플리케이션 모델은 분리할 수 없을까

DB가 범용 모델이어도 애플리케이션 내부에서는 이벤트별 책임을 분리할 수 있다고 봤습니다.

```text
Generic Event Table
        ↓
 Repository / Mapper
        ↓
 Application Domain
 ├─ Attendance
 ├─ Random Reward
 └─ Entry
```

초기에는 이 구조로 재정의했지만, 이후 애플리케이션 모델도 DB 구조와 동일하게 맞춰달라는 요구가 있었고 기존 구조를 삭제한 뒤 다시 구현했습니다.

## 적용하지 못한 설계

동시 참여와 보상 처리에서는 Redis 기반 동시성 제어를, 인증 흐름에서는 JWT 활용을 검토하고 설계했습니다. 다만 최종 운영 구조에는 반영되지 않았기 때문에 **구현 경험이 아니라 설계·제안 경험**으로 구분합니다.

## 운영 환경

```text
Client
  ↓
ALB
  ↓
ECS (EC2)
  ↓
Spring Boot Event API
  ↓
PostgreSQL

Logs → ELK
```

MAU 약 **16만**, DAU 약 **9,700** 환경에서 운영했고, 7일 이벤트 기준 총 응모 **10,950건**, 참여 회원 **6,305명**을 처리했습니다.

## 이 경험에서 중요하게 본 것

고객이나 의사결정자가 있는 환경에서는 기술적으로 더 좋은 구조라고 생각해도 그것만으로 결정되지 않습니다.

```text
기술적 대안
   +
기존 조직 방식
   +
일정 / 변경 비용
   +
의사결정자의 요구
   ↓
실제로 구현 가능한 구조
```

대안을 설명하고 충분히 대화하되, 최종 결정 이후에는 그 제약 안에서 구현을 완료하는 것도 엔지니어링의 일부라고 배웠습니다.
