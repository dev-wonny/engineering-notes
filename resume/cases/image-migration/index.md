# Legacy Image Migration & Policy

> 규칙이 일관되지 않은 레거시 이미지 구조를 **DB 데이터와 실제 화면을 대조해 역추적**하고, 이관·백업·검증과 신규 운영 정책까지 정리했습니다.

## 한눈에 보기

### 문제
Weed 레거시 쇼핑몰은 이미지가 테이블·컬럼·데이터 조건에 따라 보이거나 보이지 않았고, 저장 경로 역시 일관되지 않았습니다. DB 경로만 추출해서는 실제 서비스에서 필요한 이미지를 판단하기 어려웠습니다.

동시에 신규 쇼핑몰에서는 이미지 업로드 이후 **원본 보존, Resize 생성, 저장 경로, CDN 전달 방식**이 명확하게 정리되어 있지 않았습니다.

### 판단
먼저 **DB Row → 실제 파일 → 실제 화면 노출**을 연결해 레거시 규칙부터 찾아야 했습니다. 이후 기획자와 보존 범위를 확정하고, 그 규칙을 기준으로 마이그레이션과 검증을 구성했습니다.

신규 운영 구조는 단순히 기존 구조를 복사하지 않고, 이미지 생성 시점과 예상 처리량을 기준으로 **S3 / CloudFront 전달 구조와 Lambda 기반 온디맨드 Resize 가능성까지 함께 검토**했습니다.

### 한 일
- 이미지 관련 테이블과 실제 쇼핑몰 화면을 대조해 노출 규칙 역추적
- 기획자와 반드시 보존해야 하는 이미지 유형·이관 범위 확정
- DB에서 이미지 정보를 추출해 백업 데이터셋 구성
- 파악한 규칙을 기반으로 마이그레이션 스크립트 작성 및 결과 검증
- 쿠팡·네이버·토스 등 주요 서비스의 이미지 URL·리사이징 방식을 비교
- Butter의 현재 구현과 변경 가능한 범위를 고려해 Temp, 원본, Resize, 경로 정책 제안
- 이미지 Resize 처리 방식 논의에서 **Lambda 기반 온디맨드 처리와 예상 호출량·비용 구조 검토**

### 결과
레거시에 숨어 있던 암묵적 규칙을 **검증 가능한 마이그레이션 기준과 신규 서비스의 명시적 운영 정책**으로 바꿨습니다.

---

## 1. DB만 보면 실제 사용 이미지를 알 수 없었다

같은 이미지 도메인에서도 저장 위치와 노출 조건이 달랐습니다.

```text
DB Row
  ↓
저장 경로 확인
  ↓
실제 파일 확인
  ↓
쇼핑몰 화면 확인
  ↓
노출 조건 / 예외 규칙 기록
  ↓
이관 대상 여부 결정
```

그래서 테이블별 데이터를 직접 확인하고 실제 화면을 켜서 어떤 조건일 때 어떤 이미지가 사용되는지 비교했습니다.

| 확인 대상 | 확인한 내용 |
| --- | --- |
| 테이블 / 컬럼 | 어떤 도메인의 이미지 정보인가 |
| DB 조건 | 데이터가 있어도 화면에서 제외되는 조건은 무엇인가 |
| 저장 경로 | 동일 도메인에서도 경로가 왜 다른가 |
| 실제 화면 | 실제 고객 화면에서 사용되는가 |
| 이관 여부 | 신규 서비스에서 반드시 보존해야 하는가 |

기획자와 함께 **서비스 관점에서 반드시 남겨야 하는 이미지**를 확정한 뒤 이관 범위를 결정했습니다.

---

## 2. 백업과 마이그레이션 검증

확정한 규칙으로 DB에서 필요한 이미지 정보를 추출해 이관 전 백업 데이터를 만들고, 마이그레이션 스크립트를 작성했습니다.

```text
Weed DB
  ↓ 이미지 정보 추출
Backup Dataset
  ↓ 규칙 기반 Migration Script
S3 Migration Result
  ↓ 원천/결과 비교
Validation Dataset
```

검증 규모는 다음과 같습니다.

| 구분 | 건수 |
| --- | ---: |
| 원본 이미지 | **15,736** |
| 생성 결과 이미지 | **73,401** |
| HTML URL 치환 | **5,053** |

파일 개수만 맞추는 것이 아니라 원천 데이터와 결과를 다시 비교할 수 있도록 검증 기준을 별도로 두었습니다.

---

## 3. 이관 이후 신규 이미지 정책도 비어 있었다

마이그레이션이 끝나도 신규 쇼핑몰에서 이미지를 어떻게 운영할지는 별도 문제였습니다.

특히 커머스에서는 이미지를 먼저 업로드하고 상품·배너 같은 실제 도메인이 나중에 생성될 수 있습니다.

```text
Image Upload
    ↓
Temp 영역
    ↓
상품 / 배너 등 Domain 생성
    ↓
운영 경로로 이동
```

당시 다음 항목이 명확히 정해져 있지 않았습니다.

- 도메인 생성 전 이미지를 어디에 둘 것인가
- 원본 이미지를 보존할 것인가
- 어떤 크기의 Resize 이미지를 만들 것인가
- 비율을 유지할 것인가, 정사각형으로 자를 것인가
- 작은 원본을 확대할 것인가
- 파일명과 저장 경로를 어떻게 정할 것인가
- Resize를 애플리케이션에서 처리할지, 요청 기반 별도 컴퓨팅으로 처리할지

---

## 4. 주요 서비스 사례를 보고 현재 시스템에 맞게 조정

내부 구현만 보고 결정하지 않고 쿠팡·네이버·토스 등 주요 서비스의 실제 이미지 URL과 제공 방식을 비교했습니다.

분석 포인트는 다음과 같았습니다.

| 관점 | 확인 내용 |
| --- | --- |
| URL | 원본과 Resize 이미지가 어떻게 식별되는가 |
| Resize | width/size가 URL이나 파일명에 표현되는가 |
| 원본 | 원본과 파생 이미지 관계는 어떻게 보이는가 |
| 전달 | CDN을 통해 어떤 형태로 제공되는가 |

하지만 외부 사례를 그대로 복제하지 않았습니다. Butter에서 이미 구현한 업로드 구조와 변경 가능한 범위를 확인하고 **현재 일정과 시스템에서 실제 적용 가능한 정책**으로 조정했습니다.

---

## 5. 정리한 운영 기준

대표 이미지 기준으로 원본을 별도로 보존하고 원본을 기준으로 Resize 이미지를 생성하도록 정리했습니다.

```text
Original
  ├─ 1000px
  ├─ 600px
  └─ 100px
```

리사이징 원칙:

- 가로·세로 비율 유지
- 강제 정사각형 변환 금지
- 작은 원본 확대 금지
- 원본 별도 보존

또한 **마이그레이션 검증용 이미지 경로와 신규 서비스 운영 경로를 분리**했습니다. 일회성 이관 구조가 장기 운영 표준으로 굳어지는 것을 피하기 위해서였습니다.

---

## 6. Lambda 기반 Resize도 비용 관점에서 검토했습니다

Resize 처리 방식을 논의하면서 **Lambda를 사용하면 비용이 과도하지 않을지** 개발 리더와 확인했습니다.

검토의 핵심은 특정 서비스를 쓰는 것 자체가 아니라 다음이었습니다.

```text
이미지 Resize 요청 발생
        ↓
상시 서버에서 처리할 것인가?
        or
요청이 있을 때만 실행할 것인가?
        ↓
예상 호출량 / 실행시간 / 운영비 비교
```

당시 예상 처리량에서는 Lambda의 무료 사용 구간을 활용하면 **Resize 실행 비용이 매우 낮거나 사실상 무료 범위에 들어갈 가능성이 높다**는 설명을 확인했습니다.

다만 이미지 처리 전체 비용을 `Lambda = 무료`로 단순화하지는 않았습니다. 실제 운영에서는 다음 비용이 별도로 존재할 수 있기 때문입니다.

- S3 요청 및 저장
- CloudFront 전송
- Lambda 호출량과 실행시간
- 이미지 생성 후 파생 파일 저장량

따라서 이력서에서는 Lambda를 구현 기술로 과장하지 않고, **이미지 Resize 방식과 비용을 검토한 선택지**로만 표현했습니다.

---

## 이 경험에서 중요하게 본 것

이 작업에서 가장 어려운 것은 S3에 파일을 복사하는 일이 아니었습니다.

```text
Legacy Observation
       ↓
Rule Discovery
       ↓
Stakeholder Confirmation
       ↓
Benchmark
       ↓
Current System Constraints
       ↓
Operating Policy
```

**오래된 시스템의 암묵적 규칙을 찾아내고, 그것을 새로운 시스템이 이해할 수 있는 명시적 정책으로 바꾸는 과정**이 핵심이었습니다.
