# Commerce Product Domain Migration

> 겉으로는 모두 `Product`라고 불리지만, **변경되는 이유와 사용하는 주체가 다르면 같은 도메인 모델로 보기 어렵다**고 판단했습니다.

## 한눈에 보기

### 문제
같은 회사의 업무를 지원하지만 서로 다른 외부 시스템과 DB로 운영되던 **Weed**와 **발주모아**의 상품 데이터를 신규 플랫폼 Butter로 통합해야 했습니다.

- **Weed**: 고객이 실제로 보는 쇼핑몰 상품 페이지와 전시·판매 정보를 관리하는 외주 쇼핑몰 시스템
- **발주모아**: 공급사·발주를 관리하는 별도 SaaS로, 하나의 판매 상품에 여러 공급사가 연결되거나 기간·오픈마켓·임시 공급사 변경 등 내부 운영 정책에 따라 공급 관계가 달라질 수 있는 시스템

Butter에서는 이미 두 성격을 하나의 `Product` 테이블과 모델로 통합하는 방향으로 구현이 진행되고 있었습니다.

### 판단
두 시스템 모두 이름은 `상품`이지만 실제 책임과 수명주기가 달랐습니다.

현재 Butter의 `Product` 하나가 사실상 다음 책임을 함께 가지게 된다고 봤습니다.

- Display Product 역할
- Supply Product 역할
- Market Product 일부 역할
- 주문·정산 기준

고객에게 보이는 상품, 실제 공급 상품, 외부 마켓의 상품 식별자와 주문·정산 기준이 하나의 모델에 섞이면 **변경 이유와 식별자 의미가 서로 충돌할 수 있다**고 판단했습니다.

### 한 일
- Weed와 발주모아 실제 데이터를 비교해 판매 상품 ↔ 공급 상품 간 **1:1 · 1:N · N:1 관계** 분석
- 사업자번호·업체명·상품코드 기준 매핑 규칙과 예외 조건 정리
- CTO에게 판매/전시 상품과 공급 상품의 성격이 다르다는 점과 분리 필요성 설명
- `DisplayProduct / DisplaySku / SupplyProduct / SupplySku / MarketProduct / MarketSku`로 책임을 분리하는 대안 모델을 별도로 정리
- `DisplaySupplySkuMap`을 통해 전시 SKU와 공급 SKU를 관계로 연결하는 구조 제안
- 기존 Butter의 단일 `Product` 구조를 유지할 경우 광고·오픈마켓·공급사 변경·주문/정산 기준에서 생길 수 있는 식별자 충돌 리스크 분석
- 최종적으로 기존 통합 모델 유지 결정을 수용하고, 향후 재설계를 위한 근거와 개선안을 문서화

### 결과
당시에는 이미 Butter 구현이 상당 부분 진행되어 있었고 최종 의사결정도 단일 `Product` 유지였기 때문에 제안 구조는 적용되지 않았습니다. 다만 **겉으로 같은 이름의 데이터라도 실제 도메인 책임을 분리해서 봐야 한다는 분석과 향후 개선 가능한 대안 모델**을 남겼습니다.

## 1. A + B를 C에 넣는 문제

```text
A. Weed                         B. 발주모아
외주 쇼핑몰                     별도 SaaS
고객 노출/판매 상품             공급·발주 상품
     │                              │
     └──────────────┬───────────────┘
                    ↓
              C. Butter
            신규 커머스 플랫폼
```

처음에는 두 원천의 `상품`을 신규 상품 테이블에 넣는 데이터 마이그레이션 문제처럼 보였습니다.

하지만 실제 데이터를 보면서 먼저 확인한 것은 다음이었습니다.

> **두 시스템 모두 Product라고 부르는데, 정말 같은 Product인가?**

---

## 2. Weed Product와 발주모아 Product는 성격이 달랐습니다

### Weed Product
고객이 실제 쇼핑몰에서 보는 상품 페이지의 정체성에 가깝습니다.

```text
고객
 ↓
상품 상세 페이지
 ↓
Weed Product
```

상품명, 노출, 판매 단위, 광고에서 사용하는 상품 식별자처럼 **고객-facing 상품**의 성격이 강했습니다.

### 발주모아 Product
실제 공급과 발주를 위한 내부 상품의 성격이 강했습니다.

하나의 판매 상품이라도 실제 공급 관계는 다음처럼 바뀔 수 있습니다.

```text
고객이 보는 상품: 천도복숭아
        │
        ├─ 기간 A → 공급사 A 상품
        ├─ 기간 B → 공급사 B 상품
        ├─ 오픈마켓 운영용 공급 관계
        └─ 임시 공급사 변경
```

즉 판매 상품 하나와 공급 상품 하나가 항상 1:1인 구조가 아니었습니다.

| 시스템 | Product의 역할 | 변경되는 이유 |
| --- | --- | --- |
| Weed | 고객에게 보이는 판매·전시 상품 | 전시/판매 정책, 고객 화면, 광고 |
| 발주모아 | 공급사·발주와 연결되는 공급 상품 | 공급사, 기간, 내부 운영 정책 |
| 외부 Market | 채널별 판매 상품/SKU | 외부 채널 식별자와 운영 정책 |

이 차이 때문에 **같은 이름의 Product를 하나의 도메인 객체로 합치는 것이 맞는지** 의문을 가졌습니다.

---

## 3. 실제 관계는 1:1만 존재하지 않았습니다

원천 데이터를 기준으로 다음 관계를 모두 고려해야 했습니다.

```text
Weed Product ── 1 : 1 ── Supply Product
Weed Product ── 1 : N ── Supply Products
Weed Products ─ N : 1 ── Supply Product
```

| 관계 | 의미 | 확인해야 할 것 |
| --- | --- | --- |
| 1:1 | 판매상품 하나와 공급상품 하나 | 직접 매핑 가능 여부 |
| 1:N | 판매상품 하나에 여러 공급상품 | 공급사·기간·운영 조건별 관계 |
| N:1 | 여러 판매상품이 하나의 공급상품과 연결 | 정말 같은 상품인지 업무 의미 확인 |

사업자번호를 우선 기준으로 보고, 누락되거나 비정상적인 경우 업체명 정규화 등 보조 기준을 사용했습니다. 상품 역시 코드만으로 판단하지 않고 실제 데이터와 운영 의미를 함께 확인했습니다.

---

## 4. 기존 Butter Product에서 본 책임 집중

제가 문제라고 본 것은 단순히 컬럼이 많다는 것이 아니라 **서로 다른 이유로 변경되는 책임이 하나의 Product에 모인다는 점**이었습니다.

```text
현 Butter Product
 ├─ Display Product 역할
 ├─ Supply Product 역할
 ├─ Market Product 역할 일부
 └─ 주문 / 정산 기준
```

예를 들어 공급사가 바뀌는 것은 고객이 보는 상품 자체가 바뀌는 것과 다른 사건입니다. 오픈마켓에서 사용하는 SKU 식별자가 바뀌는 것 역시 내부 공급 상품이 바뀌는 것과 다른 문제입니다.

이 책임이 하나의 `Product`에 묶이면 다음과 같은 질문이 계속 생길 수 있다고 봤습니다.

- 공급사가 바뀌면 Product 자체가 바뀌어야 하는가?
- 광고에서 사용하는 상품코드는 Display 기준인가 Supply 기준인가?
- 오픈마켓 SKU는 어떤 Product 식별자에 연결되는가?
- 주문·정산 시점의 공급 관계를 어떻게 보존할 것인가?

---

## 5. 혼자 별도로 정리한 개선 모델

최종 구현은 통합 Product로 진행되었지만, 이후 구조를 다시 검토할 수 있도록 **역할별 Product/SKU를 분리하고 관계로 연결하는 모델**을 별도로 정리했습니다.

```text
DisplayProduct
    │
    ├──< DisplaySku
    │        └──< DisplaySupplySkuMap >──┐
    │                                    │
    ▼                                    ▼
MarketSku                           SupplySku
    ▲                                    │
    │                                    │
MarketProduct                      SupplyProduct
                                         │
                                         ▼
                                      Supplier
```

이 모델에서 각 책임은 다음처럼 분리됩니다.

| 모델 | 책임 |
| --- | --- |
| DisplayProduct | 고객에게 보이는 상품의 정체성 |
| DisplaySku | 고객이 구매하는 판매 단위 |
| SupplyProduct | 공급 관점의 상품 |
| SupplySku | 실제 공급·발주 단위 |
| DisplaySupplySkuMap | 판매 SKU와 공급 SKU의 관계 및 변경 가능성 표현 |
| MarketProduct / MarketSku | 외부 오픈마켓에서 사용하는 상품/SKU 식별자 |
| Supplier | 실제 공급 주체 |

핵심은 **판매/전시, 공급, 외부마켓 책임을 분리하면서도 매핑 관계를 통해 연결할 수 있게 하는 것**입니다.

이렇게 보면 공급사가 바뀌어도 DisplayProduct의 정체성은 유지할 수 있고, 외부 마켓의 식별자 역시 공급 상품과 억지로 같은 식별자를 공유하지 않아도 됩니다.

---

## 6. 제안은 했지만 최종 결정은 통합 Product였습니다

Weed 상품과 발주모아 상품은 성격이 다르기 때문에 분리하는 편이 낫다고 CTO에게 설명했습니다. 하지만 프로젝트의 최종 방향은 기존처럼 하나의 Product 모델로 통합하는 것이었고, Butter도 이미 해당 구조로 상당 부분 구현을 진행한 상태였습니다.

그래서 당시에는 구조를 다시 뒤집기보다 **최종 의사결정을 수용해 통합 구조 기준으로 마이그레이션을 준비하고 검증**했습니다.

동시에 향후 문제가 다시 드러날 수 있는 지점을 별도로 정리했습니다.

- 광고에서 사용하는 Weed 상품코드의 의미
- 외부 오픈마켓 Product/SKU와 내부 Product의 관계
- 한 판매상품에 여러 공급사가 연결되는 경우
- 기간별 공급사 변경
- 주문·정산 당시의 공급 관계 보존

즉 제안이 채택되지 않았다는 사실보다, **결정된 구조 안에서 프로젝트를 진행하면서도 구조적 리스크와 개선 대안을 계속 추적했다는 점**이 중요했습니다.

---

## 7. 마이그레이션 검증

최종 통합 구조를 기준으로 실제 이관도 계속 검증했습니다.

```text
Weed ──────────┐
               ├→ Mapping Rule → Butter PostgreSQL → DEV/STG 검증
발주모아 ───────┘
```

- 사업자번호·업체명·상품코드 기반 매핑
- 누락 데이터 확인
- 중복 매핑 확인
- 1:N / N:1 예외 확인
- DEV/STG 결과 비교

---

## 이 경험에서 중요하게 본 것

데이터 마이그레이션에서 컬럼 이름이나 타입이 같다고 같은 개념이라고 볼 수는 없었습니다.

```text
'Product' → 'Product'
```

처럼 보여도 실제 역할을 보면:

```text
Display Product
Supply Product
Market Product
```

라는 서로 다른 문제일 수 있습니다.

그래서 시스템을 통합할 때는 **데이터가 무엇이라고 불리는지보다, 누가 사용하고 어떤 이유로 변경되는지**를 먼저 확인해야 한다고 생각합니다.
