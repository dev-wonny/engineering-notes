# Commerce Data Migration & Domain Mapping

> Weed와 발주모아의 `상품`은 이름은 같지만 역할이 달랐습니다. 실제 데이터의 **1:1 · 1:N · N:1 관계와 식별자 의미**를 분석하고, 판매상품과 공급상품을 분리하는 대안을 제안했습니다.

## 한눈에 보기

### 문제
기존 쇼핑몰 **Weed(A)**와 발주·공급 시스템 **발주모아(B)**의 데이터를 신규 플랫폼 **Butter(C)**의 하나의 상품 구조에 통합해야 했습니다.

### 판단
두 시스템 모두 `상품`이라는 이름을 사용하지만 실제 의미가 달랐습니다. Weed는 고객이 보는 **판매상품**, 발주모아는 공급업체·발주와 연결되는 **공급상품**의 성격이 강했습니다. 단순히 상품코드끼리 합치면 향후 광고·오픈마켓 연동에서 식별자 의미가 충돌할 수 있다고 판단했습니다.

### 한 일
- 실제 데이터를 기준으로 1:1 · 1:N · N:1 매핑 관계 분석
- 사업자번호·업체명·상품코드의 매핑 우선순위와 예외 기준 정리
- 판매상품과 공급상품을 별도 모델로 두고 관계로 연결하는 구조 제안
- 최종 통합 모델 결정을 수용하면서 DEV/STG 마이그레이션 정합성 검증
- 이후 광고·오픈마켓 요구에서 발생 가능한 상품 식별자 충돌 사례 분석
- 즉시 구조 변경이 어려워 대안과 리스크를 후속 개선 자료로 문서화

### 결과
구조 변경 자체는 적용하지 못했지만, 데이터 이관을 단순 ETL로 보지 않고 **각 시스템에서 데이터가 어떤 역할을 하는지**를 기준으로 매핑과 구조적 리스크를 설명할 수 있는 근거를 만들었습니다.

## A + B를 C에 넣는 문제

```text
A. Weed                 B. 발주모아
기존 쇼핑몰              발주·공급 관리
     │                       │
     └──────────┬────────────┘
                ↓
          C. Butter
       신규 커머스 플랫폼
```

처음에는 두 원천의 `상품`을 신규 상품 테이블에 넣는 문제처럼 보였습니다. 실제 데이터를 확인하면서 먼저 물었던 질문은 다음이었습니다.

> **두 시스템 모두 상품이라고 부르는데, 정말 같은 상품인가?**

---

## 판매상품과 공급상품은 역할이 달랐다

고객 화면에서는 `천도복숭아` 하나가 보이지만 내부 공급 주체는 달라질 수 있습니다.

```text
고객이 보는 상품
천도복숭아 (Weed 판매상품)
       │
       ├─ 기간 A → A업체 천도복숭아 (발주모아 공급상품)
       └─ 기간 B → B업체 천도복숭아 (발주모아 공급상품)
```

| 시스템 | 상품의 역할 | 주요 식별 의미 |
| --- | --- | --- |
| Weed | 고객에게 노출되는 판매상품 | 판매 화면·광고 등에서 사용하는 상품코드 |
| 발주모아 | 업체·발주와 연결되는 공급상품 | 실제 공급 주체와 발주 단위 |
| Butter | 두 원천을 하나의 상품 모델로 통합 | 어느 식별자를 기준으로 할지 모호해질 수 있음 |

즉 고객에게 보이는 상품의 정체성과 내부에서 공급하는 상품의 정체성이 항상 1:1이 아니었습니다.

---

## 실제 매핑은 1:1만 존재하지 않았다

원천 데이터를 비교해보면 다음 관계를 모두 고려해야 했습니다.

```text
Weed Product ── 1 : 1 ── Supply Product
Weed Product ── 1 : N ── Supply Products
Weed Products ─ N : 1 ── Supply Product
```

| 관계 | 의미 | 확인해야 할 것 |
| --- | --- | --- |
| 1:1 | 판매상품 하나와 공급상품 하나 | 직접 매핑 가능 여부 |
| 1:N | 판매상품 하나에 여러 공급상품 | 공급사·기간·조건별 관계 |
| N:1 | 여러 판매상품이 하나의 공급상품과 연결 | 합칠 수 있는 상품인지 실제 의미 확인 |

사업자번호를 우선 기준으로 보고, 누락되거나 비정상적인 경우 업체명 정규화 등 보조 기준을 함께 사용했습니다. 상품 역시 코드만으로 판단하지 않고 실제 데이터와 운영 의미를 확인했습니다.

---

## 초기 제안: 두 상품을 관계로 연결

제가 제안한 방향은 판매상품과 공급상품을 하나로 압축하는 대신 별도로 두는 구조였습니다.

```text
SellProduct
    │
    │ supply / sourcing relation
    ↓
SupplyProduct
    │
    ↓
Supplier
```

이 구조에서는 고객이 보는 `천도복숭아`의 정체성을 유지하면서 공급 업체가 바뀌면 공급 관계만 변경할 수 있습니다.

| 변화 | 분리 모델 | 통합 모델에서 고려할 점 |
| --- | --- | --- |
| 공급사 변경 | 관계 변경 | 상품 자체 변경인지 판단 필요 |
| 공급기간 변경 | 공급 관계 이력 | 한 상품에 공급 정보가 섞일 수 있음 |
| 광고 적용 | 판매상품 코드 사용 | 어떤 상품코드를 기준으로 할지 필요 |
| 오픈마켓 연동 | 판매상품/SKU 관계 정의 | 내부 공급상품과 외부 판매상품의 기준 충돌 가능 |

초기에는 이 이유로 상품 모델을 분리하자고 제안했지만, 프로젝트의 최종 결정은 하나의 상품 모델로 통합하는 것이었습니다.

---

## 시간이 지나며 다시 나타난 식별자 문제

이후 광고 적용을 검토할 때 상품을 식별하는 기준이 Weed의 상품코드라는 점이 다시 중요해졌습니다.

```text
광고 시스템
    ↓
Weed 상품코드로 상품 식별
    ↓
신규 통합 상품에서는?
    ↓
판매상품 코드인가 / 공급상품 코드인가
```

오픈마켓 연동에서도 같은 문제가 생길 수 있습니다. 외부 채널의 상품이나 SKU가 고객에게 보이는 판매상품과 연결되는지, 내부 공급 단위와 연결되는지를 명확히 해야 하기 때문입니다.

이 시점에는 Butter의 구현이 상당 부분 진행돼 데이터 모델을 바꾸는 비용이 큰 상태였습니다. 주변 기획자와 개발자에게 문제와 대안을 공유했지만 즉시 구조 변경을 추진하기보다는 **식별자 충돌 사례와 대안 모델을 자료로 남겼습니다.**

## 마이그레이션 검증

최종 통합 구조를 기준으로 실제 이관도 계속 검증했습니다.

```text
Weed ──────────┐
               ├→ Mapping Rule → Butter PostgreSQL → DEV/STG 검증
발주모아 ───────┘
```

- 사업자번호·업체명·상품코드 기반 매핑
- 누락 데이터 확인
- 중복 매핑 확인
- 1:N / N:1 예외 확인
- DEV/STG 결과 비교

---

## 이 경험에서 중요하게 본 것

데이터 마이그레이션에서 컬럼 이름이나 타입이 같다고 같은 개념이라고 볼 수는 없었습니다.

```text
'상품' → '상품'
```

처럼 보이는 매핑도 실제 업무 의미를 확인하면:

```text
판매상품 → ?
공급상품 → ?
```

이라는 다른 문제가 됩니다.

그래서 시스템을 통합할 때는 **데이터가 무엇이라고 불리는지보다 그 시스템 안에서 어떤 역할을 하는지**를 먼저 확인해야 한다고 생각합니다.
