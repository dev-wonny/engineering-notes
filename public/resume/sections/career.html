문제

외부 개발사 Butter의 기존 Batch는 백엔드 내부 Quartz Scheduler 중심으로 구성되어 있었고, 이후 일부 Job은 AI 기반으로 재작성됐지만 주문·회원·통계 정책이 명확하지 않았습니다.

판단

단순히 Quartz를 Airflow로 교체하는 것이 아니라 스케줄링 책임, 실행 환경, 데이터 접근 방식, 정책 검증을 함께 분리해야 한다고 판단했습니다.

구조 개선
  • Quartz 대신 Jenkins 또는 Airflow 기반 외부 스케줄링 구조 제안 후 Airflow 구조로 운영
  • API 로직에 섞여 있던 정기 처리 로직을 Batch Job으로 분리
  • EC2 Airflow → ECS Fargate → Spring Batch 실행 구조 운영
  • Spring Batch를 상시 기동하지 않고 Job 실행 시 Fargate Task로 기동
  • 시스템 간 시간 기준 차이를 줄이기 위한 Zero Offset 기준 통일 방안 제안
  • 대량 처리의 JPA 영속성 컨텍스트 부담을 고려해 쿼리 중심 처리를 제안했고 최종 MyBatis 채택
정책 검증
  • 기존 코드·원천 데이터·결과 데이터를 비교해 주문·회원·통계 집계 조건 검증
  • 잘못된 상태값·포함/제외 조건 수정
  • 재실행·Backfill 시 데이터 중복·누락과 멱등성 검증
  • Docker + PostgreSQL + LocalStack 기반 로컬 검증 환경 구성
결과

스케줄링·실행 환경과 도메인 정책을 분리하고 실제 데이터 기준으로 검증 가능한 Batch 구조로 정리하고 있습니다.
