Batch Platform 재설계 및 정책 검증2026.07 ~ 진행중
Spring Batch · Airflow · AWS EC2 · ECS Fargate · PostgreSQL · MyBatis · Docker · LocalStack
배경

기존 외부 개발사 구조는 백엔드 애플리케이션 내부 Quartz Scheduler 중심이었고, 이후 AI 기반으로 재작성된 Batch도 주문·회원·통계 정책이 명확하지 않았습니다.

구조 개선
  • Quartz 대신 Jenkins 또는 Airflow 기반 외부 스케줄링 구조를 제안하고 최종 Airflow 구조로 운영
  • API 로직에 섞여 있던 정기 처리 로직을 Batch Job으로 분리
  • EC2 Airflow → ECS Fargate → Spring Batch 실행 구조 운영
  • Spring Batch를 상시 기동하지 않고 Job 실행 시 Fargate Task로 기동
  • Zero Offset 기준 통일 방안 제안
  • 대량 처리의 JPA 영속성 컨텍스트 부담을 고려해 쿼리 중심 처리를 제안했고 최종 MyBatis 채택
정책 검증
  • 코드·원천 데이터·결과 데이터를 비교해 집계 조건 검증
  • 잘못된 상태값·포함/제외 조건 수정
  • 재실행·Backfill 시 데이터 중복·누락과 멱등성 검증
  • Docker + PostgreSQL + LocalStack 기반 로컬 검증 환경 구성
결과

스케줄링·실행 환경과 도메인 정책을 분리하고 실제 데이터 기준으로 검증 가능한 Batch 구조로 정리하고 있습니다.

문제

Weed 레거시는 테이블과 조건마다 이미지 저장 경로와 화면 노출 규칙이 달라 DB만으로 실제 이관 대상을 판단하기 어려웠고, 신규 플랫폼의 이미지 업로드·보관·Resize·전달 기준도 정리되어 있지 않았습니다.

판단

실제 화면과 DB 데이터를 대조해 레거시 사용 규칙을 역추적하고, 이관 과정에서 확인한 기준을 신규 이미지 저장·전달 정책까지 연결해야 한다고 판단했습니다.

한 일
  • 상품·상세·배너·쿠폰 등 이미지 유형별 DB 데이터와 실제 화면 노출 결과 비교
  • 기획자와 보존 대상 범위를 확정하고 DB 기반 백업 데이터 및 마이그레이션 스크립트 작성
  • 원본 15,736건, 결과 이미지 73,401건, HTML URL 치환 5,053건 검증
  • 마이그레이션용 경로와 장기 운영용 이미지 경로를 분리
  • Temp → 도메인 생성 후 운영 경로 이동, UUID 기반 파일명·URL 규칙, 원본 보존 정책 정리
  • 대표 이미지 기준 1000px / 600px / 100px Resize, 비율 유지, 확대 금지 정책 정리
  • 쿠팡·네이버·토스 사례를 비교해 현재 시스템과 외부 개발사가 적용 가능한 수준으로 정책 조정
  • S3 / CloudFront 기반 이미지 제공 흐름과 외부 개발사 간 책임 범위 조율
  • Resize 처리 방식 논의에서 Lambda 기반 온디맨드 처리와 예상 호출량·비용 구조를 검토
결과
