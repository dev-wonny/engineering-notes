문제

Weed 레거시는 테이블과 조건마다 이미지 저장 경로와 화면 노출 규칙이 달라 DB만으로 실제 이관 대상을 판단하기 어려웠고, 신규 플랫폼의 이미지 업로드·보관·Resize·전달 기준도 정리되어 있지 않았습니다.

판단

실제 화면과 DB 데이터를 대조해 레거시 사용 규칙을 역추적하고, 이관 과정에서 확인한 기준을 신규 이미지 저장·전달 정책까지 연결해야 한다고 판단했습니다.

한 일
  • 상품·상세·배너·쿠폰 등 이미지 유형별 DB 데이터와 실제 화면 노출 결과 비교
  • 기획자와 보존 대상 범위를 확정하고 DB 기반 백업 데이터 및 마이그레이션 스크립트 작성
  • 원본 15,736건, 결과 이미지 73,401건, HTML URL 치환 5,053건 검증
  • 마이그레이션용 경로와 장기 운영용 이미지 경로를 분리
  • Temp → 도메인 생성 후 운영 경로 이동, UUID 기반 파일명·URL 규칙, 원본 보존 정책 정리
  • 대표 이미지 기준 1000px / 600px / 100px Resize, 비율 유지, 확대 금지 정책 정리
  • 쿠팡·네이버·토스 사례를 비교해 현재 시스템과 외부 개발사가 적용 가능한 수준으로 정책 조정
  • S3 / CloudFront 기반 이미지 제공 흐름과 외부 개발사 간 책임 범위 조율
  • Resize 처리 방식 논의에서 Lambda 기반 온디맨드 처리와 예상 호출량·비용 구조를 검토

문제

고객 노출 상품을 관리하는 Weed와 공급·발주를 관리하는 별도 SaaS 발주모아의 상품 데이터를 신규 플랫폼의 단일 Product 모델로 통합해야 했습니다.

판단

두 시스템 모두 Product라고 부르지만 실제 책임과 변경 이유가 달랐습니다.

  • Weed: 고객이 보는 상품 페이지와 전시·판매 상품
  • 발주모아: 공급사·기간·오픈마켓·임시 공급사 변경 등 운영 정책에 따라 관계가 달라지는 공급 상품

Display·Supply·Market·주문/정산 기준을 하나의 Product에 모으면 식별자와 변경 책임이 섞일 수 있다고 판단했습니다.

한 일
  • 실제 데이터에서 판매 상품 ↔ 공급 상품 간 1:1 / 1:N / N:1 관계 분석
  • 사업자번호·업체명·상품코드 기준 매핑 규칙과 예외 조건 정리
  • DisplayProduct / DisplaySku / SupplyProduct / SupplySku / MarketProduct / MarketSku로 책임을 분리하는 모델 제안
  • DisplaySupplySkuMap을 통해 전시 SKU와 공급 SKU를 관계로 연결하는 구조 별도 정리
  • 기존 단일 Product 구조 유지 시 광고·오픈마켓·공급사 변경·주문/정산 기준에서 발생 가능한 식별자 충돌 리스크 문서화
결과

이미 구현이 진행된 통합 Product 구조와 최종 의사결정을 수용해 마이그레이션을 진행하되, 향후 재설계를 위한 도메인 분리 근거와 개선안을 남겼습니다.
