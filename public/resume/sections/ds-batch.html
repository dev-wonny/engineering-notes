Batch Platform 재설계 및 정책 검증2026.07 ~ 진행중
Spring Batch · Airflow · AWS EC2 · ECS Fargate · PostgreSQL · MyBatis · Docker · LocalStack
배경

외부 개발사는 백엔드 애플리케이션 내부의 Quartz Scheduler 기반으로 배치 로직을 구성하고 있었고, 이후 일부 Batch는 AI 기반으로 재작성되었습니다. 하지만 주문·회원·통계 정책이 명확하지 않았고 API와 정기 처리 로직의 경계도 불분명했습니다.

구조 개선
  • 백엔드 내부 Quartz Scheduler 대신 Jenkins 또는 Airflow 기반 외부 스케줄링 구조를 제안하고, 최종적으로 Airflow 기반 구조로 전환
  • API 로직에 포함되어 있던 정기 처리 로직을 Batch Job으로 분리
  • Managed Airflow 비용을 고려해 EC2에 Apache Airflow를 직접 구성
  • EC2 Airflow → ECS Fargate → Spring Batch 실행 구조로 운영
  • Spring Batch 애플리케이션을 상시 기동하지 않고 Job 실행 시 ECS Fargate Task로 기동
  • Airflow·애플리케이션·DB 간 기준 시각 차이를 줄이기 위해 Zero Offset 기준 통일 방안 제안
  • 대량 처리 시 JPA 영속성 컨텍스트의 메모리 사용과 flush/clear 관리 부담을 고려해 쿼리 중심 처리를 제안했고 최종 MyBatis 채택
정책 검증
  • 기존 코드·원천 데이터·결과 데이터를 비교해 주문·회원·통계 집계 조건 검증
  • 잘못된 상태값 및 포함/제외 조건 수정
  • 재실행·Backfill 시 데이터 중복·누락 여부와 멱등성 검증
  • Docker + PostgreSQL + LocalStack 기반 로컬 검증 환경 구성
결과

단순히 스케줄대로 실행되는 Batch가 아니라 스케줄링·실행 환경과 도메인 정책을 분리하고, 실제 데이터 기준으로 검증 가능한 Batch 구조로 정리하고 있습니다.
